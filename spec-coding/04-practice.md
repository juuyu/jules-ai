# 04 实践落地

> 本章解决：把方法论用起来——完整案例、可复用模板、工具链与踩坑记录。

## 4.1 完整案例：从想法到代码

以"给博客加一个评论功能"为例，走一遍 SDD 全流程。

### Step 1 写需求 Spec（约 15 分钟）

- 目标：访客能对文章发表评论
- 用户故事：作为访客，我想对文章留言，以便与作者交流
- 验收标准：未登录可评论 / 内容非空且 ≤ 500 字 / 提交后立即展示 / 非法输入给出错误提示
- Non-goals：本期不做嵌套回复、不做通知、不做审核流
- 约束：不改动现有文章接口；移动端可用

### Step 2 出技术方案（约 10 分钟）

- 让 AI 给两个备选（评论内嵌存储 vs 独立服务）并建议其一
- 敲定：数据模型（comments 表字段）、接口（POST /comments、GET /comments?post_id=）、前端组件划分、错误处理约定

### Step 3 拆任务

```
T1 数据模型与迁移
T2 创建评论接口 + 测试      （依赖 T1）
T3 列表接口 + 测试          （依赖 T1）
T4 评论表单组件             （依赖 T2）
T5 评论列表组件             （依赖 T3）
T6 端到端验证与验收对照
```

### Step 4 逐任务实现

- 每个任务：喂「spec + 方案 + 规则文件」→ AI 实现 → 跑测试 → 提交
- 每个任务完成后更新 tasks 勾选状态

### Step 5 验收与沉淀

- 对照验收标准逐条检查（而不是凭感觉"看起来能用"）
- 把过程中的经验（AI 犯过的错、需要加的护栏）回写到规则文件

## 4.2 模板集

### spec 模板

```markdown
# 〈功能名〉需求

## 背景与目标
## 用户故事
- 作为〈角色〉，我想要〈功能〉，以便〈价值〉

## 验收标准
- [ ] ...
- [ ] ...

## Non-goals
- 本期不做 ...

## 约束
- ...
```

### plan 模板

```markdown
# 〈功能名〉技术方案

## 选型与理由
## 模块与文件
## 数据模型 / 接口
## 关键流程（正常路径 / 异常路径）
## 风险与替代方案
```

### tasks 模板

```markdown
# 〈功能名〉任务

- [ ] T1 〈描述〉（文件：... 验收：...）
- [ ] T2 〈描述〉（依赖：T1 验收：...）
```

## 4.3 工具链

- **GitHub Spec Kit**：官方工作流工具，配合 Claude Code / Copilot / Gemini CLI 等使用（详见 02-frameworks）
- **AWS Kiro**：IDE 形态，spec 工作流内置
- **OpenSpec / BMAD**：轻量与多角色两种流派
- **通用组合（不依赖框架）**：仓库建 `specs/` 目录 + 规则文件 + 手动三件套，任何 Agent 工具都能用

## 4.4 踩坑记录

- **过度 Spec**：小改动写几千字文档，得不偿失 → 按任务风险匹配 spec 粒度
- **Spec 腐坏**：写完就不管，实现与文档脱节 → 变更时先改 spec 再改代码
- **验收标准不可测**："界面美观"无法验收 → 改成可判定的具体条目
- **AI 跳出 Spec**：实现时自行加需求 → 规则文件里加一条"超出 spec 范围先提问"
- **任务切太碎**：每个任务都要重建上下文 → 按垂直切片拆，一个任务一次会话完成
