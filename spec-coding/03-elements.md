# 03 核心要素

> 本章解决：一份合格的 spec 体系包含哪几块？每份文档分别写给谁看？

## 3.1 文档全景

| 文档 | 回答的问题 | 主要读者 |
| --- | --- | --- |
| spec（需求） | 做什么？给谁用？怎么算做完？ | 人 + AI |
| design / plan（方案） | 怎么做？用什么技术？边界在哪？ | 人（主）+ AI |
| tasks（任务） | 按什么顺序做？每步怎么验收？ | AI（主）+ 人 |
| 规则文件（约束） | 一直要遵守什么？ | AI |

## 3.2 需求 Spec

**核心内容：**

- 背景与目标：为什么做、解决什么问题
- 用户故事：作为〈角色〉，我想要〈功能〉，以便〈价值〉
- 验收标准：可测试的具体条目（清单式或 Given/When/Then）
- 边界与非目标：明确"不做什么"（Non-goals 极其重要，用来砍掉 AI 的联想空间）
- 约束：性能、兼容性、合规要求

**写法要点：**

- 每条验收标准都必须"可判定真假"，避免"体验流畅"这类虚词
- Non-goals 写 3-5 条，宁多勿少
- 使用领域词汇，避免"那个模块""相关逻辑"这类模糊指代

## 3.3 技术方案（Design / Plan）

- 技术选型与理由（一句话 why，不写长篇论证）
- 架构与模块划分（哪些文件 / 模块新增或修改）
- 数据模型与接口定义（类型、函数签名、schema——AI 实现时直接照抄）
- 关键流程：正常路径 + 错误路径
- 风险与替代方案

小任务可跳过独立文档，把这几项写成 spec 附带的"实现说明"即可。

## 3.4 任务拆解（Tasks）

- **原则**：按可独立验证的垂直切片拆，不按"前端 / 后端"横切
- 每个任务包含：描述、涉及文件、验收方式、依赖关系
- **排序**：先地基（数据模型 / 接口）后功能；可选项——测试先行（TDD 式）
- **粒度**：单个任务应能在一次 Agent 会话内完成并验证

## 3.5 约束文件（AGENTS.md 等）

与 spec 的区别：spec 描述"这一件事"，约束文件描述"永远如此"。

- 技术栈版本、目录约定、常用命令
- 代码风格与架构原则（如"领域层不依赖框架"）
- 禁忌清单
- 演进方式：发现问题就追加一条，定期精简，防止膨胀

## 3.6 Spec 的维护

- **活文档**：实现中发现 spec 有错，先改 spec 再改代码
- **变更流程**：需求变了 → 更新 spec → 更新任务 → 再实现
- **粒度匹配**：不是所有任务都要全套文档。小改动用轻量 spec（几行字），大功能才上完整"三件套"
