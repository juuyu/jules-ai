# 01 概念与动机

> 本章解决：什么是 Spec 驱动开发？为什么"先写规范再让 AI 编码"成为主流方法论？

## 1.1 什么是 Spec-driven Development（SDD）

一句话：把"要做什么、怎么做、怎么算做完"先写成结构化文档，再让 AI（或人）按文档实现。

- 传统开发里文档是"事后产物"，SDD 里 spec 是"输入"——先于代码存在，驱动实现
- 在 AI 编程语境下：spec 是人给 AI 的**最高级上下文**，也是人验收 AI 的**依据**

三个常见误解：

- **≠ 需求文档大全**：SDD 的 spec 精炼、面向实现，不是把 PRD 复制粘贴一遍
- **≠ 瀑布流程回归**：spec 是可以随实现迭代的活文档，不是一次性冻结的
- **≠ 只有大项目才需要**：一个小功能写 10 行 spec，收益同样明显

## 1.2 Vibe Coding 的局限

Vibe Coding（凭感觉对话式编程）起手很快，但随着任务规模增长会遇到天花板：

| 场景 | 表现 |
| --- | --- |
| 小脚本 / Demo | 极快，问题不明显 |
| 中等功能 | 需求开始被"理解偏"，反复返工 |
| 多人协作 / 长期维护 | 无法追溯"为什么这么写"，改动失控 |
| 重构 / 大改动 | AI 缺少全局约束，改出隐藏 bug |

典型翻车模式：

- **需求漂移**：聊着聊着，实现了一个你没要的东西
- **上下文超载**：代码库一大，AI 开始幻觉出不存在的方法
- **验收缺失**："完成"了，但你没法证明它满足了需求

## 1.3 为什么 AI 编程需要 Spec

1. **对齐**：把隐式需求显式化，消灭"我以为你知道"
2. **约束**：技术选型、边界条件提前锁死，AI 没有自由发挥的空间
3. **可验证**：验收标准直接变成测试用例，AI 自己也拿它自检
4. **可追溯**：spec 在，未来任何一次改动都有参照物
5. **抗遗忘**：spec 就是最好的交接文档——新会话、新成员、新 Agent 都能从它起步

一句话总结：**Vibe Coding 用对话换速度，SDD 用文档换稳定性。** 两者不对立，按任务风险在光谱上切换。
