# 07 文档规范

> v0.1（2026-10-15）｜[规范总览](./README.md)

## 1. 文档分层与职责

| 位置 | 职责 | 更新时机 |
| --- | --- | --- |
| `README.md`（根） | 是什么、怎么装、怎么跑 | 安装 / 启动方式变更时 |
| `docs/01-requirements.md` | 需求（目标 / 功能 / 优先级） | 需求变化时 |
| `docs/02-technical-design.md` | 技术设计（架构 / 接口草案） | 架构或接口变更时 |
| `spec/*`（本目录） | 编码规范 | 规范演进时 |
| 代码注释 | 解释"为什么" | 仅必要处（见 03） |

## 2. 写作规则

- 语言：正文中文；文件名英文 kebab-case；技术术语保留英文（PTY、WebSocket）
- 格式：GFM；枚举用表格，代码块标注语言；每份文档头部一行 `> vX.Y（日期）`
- 可执行性：条目给出正例 / 反例 / 检查方式至少其一；禁止"尽量、建议、酌情"等不可验证措辞
- 篇幅：单文档聚焦一个主题；超过 200 行考虑拆分
- 事实核查：涉及 Gemini CLI 行为 / 路径的表述必须来自官方文档并附链接（见技术方案 §8），不凭记忆或博客

## 3. 注释规则

（与 03 一致，此处为唯一执行标准的补充说明）

- 默认零注释；仅在 WHY 非显然时写一行
- 禁止：描述 WHAT、任务 / issue 引用（"为 #123 添加"）、过期 TODO
- TODO 必须带负责人与日期：`// TODO(nie, 2026-10-20): 支持二进制帧`

## 4. 变更管理

- 接口 / 行为变更：同一次提交内同步更新对应文档（04 规定同步要求）
- 文档历史：头部保留 `vX.Y（日期）` 即可；MVP 不建独立 CHANGELOG
- 删除过期内容，不保留"已废弃"段落（git 历史即归档）

## 5. 禁止事项

- 编造 API / 参数 / 路径（拿不准就写 TODO 并去官方文档核实）
- 大段复制外部文档（给链接 + 一句话摘要即可）
- 文档中写与实现不符的"规划"（规划放 docs，规范只写当前约束）
