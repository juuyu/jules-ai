## 总体原则

1. **简单直接**：单用户本地工具，不为假想需求设计（不引入多余抽象、状态库、微服务）
2. **保真是底线**：终端体验与原生一致是第一优先级，任何定制不得牺牲保真
3. **以官方文档为准**：涉及 Gemini CLI 行为与路径时，先查官方文档（见 [docs/02 §8](../docs/02-technical-design.md)），不凭记忆
4. **可验证**：规范条目给出正例 / 反例 / 检查方式至少其一，禁止"尽量、建议、酌情"等无法验证的措辞

## 功能完成检查清单

每个功能（PR / 提交）完成时逐项自查：

- [ ] 目录与文件命名符合 01 / 02
- [ ] 新增接口符合 04 的统一响应格式与错误码
- [ ] 所有失败路径有用户可见反馈（05）
- [ ] 关键逻辑（lib / api）有对应测试（06）
- [ ] 接口或行为变更已同步更新文档（07）
