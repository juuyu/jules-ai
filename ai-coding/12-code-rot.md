# 12 代码腐坏治理：AI 时代的熵管理

> 本章解决：AI 编程让代码产出速度大幅提升，冗余、重复、死代码、分叉实现也在同步累积——系统腐坏从「月级」加速到「分钟级」。本章给出一套可落地的治理机制：防（生成端约束）→ 检（自动化可见）→ 治（定期低成本清理）。与 11 章同一条心法：靠机制，不靠自觉。数据与工具信息截至 2026-10-17，出处见文末。

## 12.1 现象：腐坏已经被量化

「AI 写代码会加速腐坏」不是错觉，2026 年已经有了行业级数据：

- **GitClear 2026 报告**（多家转述）：AI 编程下，复制 / 搬运式改动上升约 **40%**，重构下降约 **25%**；在覆盖率 92% 的项目中，仍有 **63%** 被 bug 击穿——所谓「覆盖率幻觉」：测试覆盖了行为，没有覆盖意图；
- **媒体转述的另一组口径**：产出 +25% 的同时，代码重复率 +81%；维护成本高出 120%（不同口径数字有出入，方向一致）；
- **「Slopfix」成为一门生意**：三位资深工程师创业专删 AI 写的代码——案例中把 10 万行删到 3.5 万行，一周报价 1 万美元，按结果付费。

一句话概括：**AI 同时加速了「写」和「堆」，但只有「写」这一半被加速了。**

## 12.2 根因：AI 腐坏的四条特殊通道

传统技术债是慢积累；AI 时代的腐坏有自己的通道，对症才能下药：

| 根因 | 表现 |
| --- | --- |
| 代谢失衡 | 生成速度 >> 清理速度，熵增从「月级」变成「分钟级」 |
| **局部视野** | 上下文里没有的 = 不存在；找不到已有实现就重写一个——语义重复的第一来源 |
| 症状级修复 | 测试通过即交差，「就地打补丁」比「重构根因」省事 |
| 会话无记忆 | 同一问题被不同会话用不同方案解决 → 分叉实现，比文本重复更隐蔽 |

第二条是重点：AI 不会主动全局搜索「是否已有」。它只会在上下文里找；找不到，就写一个新的。**重复不是它懒，是它看不到。**

## 12.3 治理框架：防 → 检 → 治

沿用 11 章的心法——腐坏不可能「防绝」，目标是把它变得**可见 + 低成本可修**。三段循环：

| 段 | 目标 | 手段 | 频率 |
| --- | --- | --- | --- |
| **防** | 生成时少制造 | 规则 + 能力索引 + 任务约束 | 每次任务 |
| **检** | 让腐坏自动可见 | CI 检查 + rot-check 技能 | 每次提交 / 定期 |
| **治** | 低成本清除 | 固定预算 + AI 清理 PR | 每迭代 / 定期 |

三段缺一不可：只防不检 → 破窗无人知；只检不治 → 报告年年有，代码年年烂；只治不防 → 边清边堆。

## 12.4 防：生成端约束（成本最低的一段）

### 复用优先规则（写进 AGENTS.md）

```markdown
## 防重复（写代码前）
- 新增函数 / 组件 / 工具类前，先检索项目中是否已有：grep 关键词、查 docs/CAPABILITIES.md
- 已有实现能覆盖大部分需求 → 扩展它，不要新写一个
- 不确定时先问，不要「先写一个差不多的」
```

### 能力清单 docs/CAPABILITIES.md

AI 重复造轮子的第一原因是「不知道轮子存在」。给可复用能力建一张索引——11 章 MAP.md 的姊妹文档（MAP 按功能域组织，CAPABILITIES 按可复用能力组织）：

```markdown
# docs/CAPABILITIES.md — 可复用能力索引
| 能力 | 位置 | 何时用 / 禁止什么 |
| --- | --- | --- |
| HTTP 请求 | packages/shared/http/ | 统一超时 / 重试 / 错误处理；禁止业务层直接 fetch |
| 日期处理 | packages/shared/date.ts | 格式化 / 时区换算；别再引入第二套日期工具 |
| 表单校验 | packages/ui/validators/ | 校验规则复用；别在业务层重写正则 |
```

「何时用 / 禁止什么」两列都要写——前者帮 AI 决定复用，后者阻断分叉。

### 任务约束模板

每次委派任务带上约束句（02 章「四要素」中的约束项）：

```text
约束：最小改动；只动与本任务相关的文件；不顺手重构无关代码；不引入新依赖。
```

这一条不能省——AI 的默认行为是「顺便优化」，而「顺便」正是分叉和老化的开始。

### 其余三防

- **spec 先行**（见 spec-coding 章节）：先收敛「做什么 / 不做什么」，减少自由发挥产生的多套实现；
- **小步 + 一次一事**（02 / 04 章）：diff 小，审查才审得动，腐坏藏不住；
- **规则沉淀循环**：每次纠正 AI → 问「这条要不要进规则、能不能变成 lint 规则」——复发问题交给自动化兜底。

## 12.5 检：让腐坏自动可见

CI 是免疫系统的传感器。按检查项配齐（前四项建议直接设为 merge gate）：

| 检查项 | 工具例 | 抓什么 |
| --- | --- | --- |
| lint / 类型 / 测试 | 各语言标配 | 基线门槛 |
| **增量覆盖率** | diff-cover、Codecov patch | 新代码必须有测试——比总覆盖率有效得多，专治覆盖率幻觉 |
| 重复代码 | jscpd、SonarQube | 文本级复制粘贴、重复率趋势 |
| 复杂度 | ESLint complexity、sonarjs 认知复杂度 | 膨胀函数 |
| 死代码 / 无人用导出 | knip（TS）、vulture（Python）、deadcode（Go） | AI 爱写「没人调用」的代码 |
| 架构边界 / 循环依赖 | dependency-cruiser、madge（JS）、import-linter（Python）、ArchUnit（Java） | 局部视野最容易破模块边界 |
| **语义重复 / 风格分叉** | rot-check 技能（见下） | 文本不重复但意图重复——AI 腐坏的特色 |

前几项都有现成工具，最后一项是天然缺口：文本工具抓不到「两个函数长得不像、但干的是同一件事」。用 11 章 drift-check 的同一模式补上——rot-check 技能：

```markdown
---
name: rot-check
description: 检查代码库腐坏迹象（语义重复、死代码、分叉模式、过度抽象）。在用户要求「代码体检 / 腐坏治理」、发版前、周期性维护时使用。
---

# 代码腐坏审查

逐项执行，**只输出报告，不修改任何代码**：

1. 跑自动化检查（重复率 / 死代码 / 复杂度），收集数字与热点文件列表
2. 语义重复：选改动最频繁的 3 个目录，找「同一意图的多份实现」（如三套日期格式化）
3. 分叉模式：找同一问题被不同方案解决的地方（如两套 HTTP 封装）
4. 过度抽象：找只有单个调用点、或从未被调用的抽象层
5. 输出按「收益 / 风险」排序的清单，每项附安全清理路径（先补什么测试、改哪些文件）
```

运行节奏与红线同 11.7：CI 定时 / 发版前跑；**检测自动、修改过审**。

## 12.6 治：把「清理」也交给 AI

被忽略的另一半：AI 让「读懂旧代码 + 重构」同样变便宜了。失衡的原因不是「AI 写得多」，而是没人用 AI 清。

**固定预算**：每迭代 / 每周留 10~20% 做「收口」，写进排期而不是愿望。清理永远是「重要不紧急」——不给预算就等于不做。

**清理动作清单**（全部 AI 执行、人审）：

- 把 N 个重复 helper 收成一个（合并实现，保留最全的那个 + 薄适配层）；
- 删除死代码与无人用的导出；
- 拉平过度抽象（单调用点的封装就地展开）；
- 统一分叉约定（两套日期工具、两套 HTTP 封装 → 收敛到 CAPABILITIES.md 里的那一个）；
- 给没有测试的旧代码补 characterization tests（先固化现状行为，再动刀）。

**安全流程**（顺序不能变）：

```text
补测试网（固化现状行为）→ AI 重构 → 跑全量测试 + 人审 diff → 合并
```

没有测试网的重构是赌博——多数人正是因为没有网，才需要花 1 万美元一周请 Slopfix。

**治理专项**：rot-check 报告 → AI 出清理 PR → 人审 → 合并（与 11 章的漂移治理同一模式）。大清理拆成多个小 PR，一步一合并，别一次吃成胖子。

另外：架构级结论进 ADR——防止同一问题被不同会话「重新发明」。

## 12.7 度量：仓库健康看板

选 4~5 个指标，**看趋势不看绝对值**：

| 指标 | 来源 |
| --- | --- |
| 重复率 / 克隆数 | jscpd、SonarQube |
| 死代码量 / 未使用导出数 | knip、vulture 等 |
| 平均 / 最高复杂度 | lint 报告 |
| 增量覆盖率 | CI |
| 定位耗时（可选） | 11 章定位题耗时 |

每月 rot-check 报告本身就是趋势数据。指标突然恶化 → 回查最近哪批改动引入的，用 12.4 的「规则沉淀」堵住。

## 12.8 反模式清单

1. **只靠「提醒 AI 别写冗余」**——约束不是口号，要进规则文件 + 检查项；
2. **等「以后专门重构」**——清理必须进排期（固定预算），否则永远不做；
3. **重构前不补测试**——赌博；先固化现状行为再动刀；
4. **让 rot-check 自动改代码**——与 11 章同一条红线：报告自动出，修改要过审；
5. **只看总覆盖率**——看增量覆盖率与语义重复；总覆盖率是「质量幻觉」的重灾区；
6. **一次性大扫除**——改动巨大、审不动、风险高；拆成小 PR 常态化；
7. **把重复率当唯一目标**——目标是「意图只有一份实现」；有些文本相似是合理的（如不同模块的薄适配层）。

## 12.9 落地清单

1. **防**：AGENTS.md 加「防重复」规则；建 `docs/CAPABILITIES.md`（先覆盖最常用的 5~10 个能力）；任务模板带约束句；
2. **检**：CI 加四大门禁（lint / 类型 / 测试 / 增量覆盖率）+ 静态检查（jscpd、knip、边界规则）；写好 rot-check 技能，挂 CI 定时；
3. **治**：排期固定 10~20% 收口预算；每月执行「rot-check 报告 → 清理 PR → 人审」循环；
4. **度**：把 12.7 指标做成月报，看趋势。
