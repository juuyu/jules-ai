# 11 项目知识库：AI 的长期项目记忆

> 本章解决：项目持续迭代，如何维护一份 AI 能长期使用的项目知识库——让每个新会话都能快速知道「项目是干什么的、功能在哪、改哪个 bug 该动哪个包」，而不是每次全库扫描。重点不在「怎么建」（一次性动作），而在「怎么维护」（长期机制）。信息截至 2026-10-17，工具支持情况经官方文档与实测文章核查。

## 11.1 心法：导航系统，不是项目百科

每次开新会话，AI 都要重新「认识」你的项目。这件事的成本随项目规模增长：

- **token 花在「找」而不是「做」**：不了解结构 → 大量搜索 → 上下文被搜索结果填满，信噪比骤降；
- **重复解释**：同一套背景（技术栈、约定、模块划分）你讲第 N 遍；
- **定位漂移**：全库扫描的结果不稳定，换会话、换模型就可能定位到不同位置。

第一反应往往是「写一份全的项目文档」。但知识库最大的风险恰恰是**腐烂**：写完那天起它就开始过时，而 AI 会毫不犹豫地相信过时的文档，按旧结构改新代码。所以先立住三条心法：

1. **代码是唯一事实源**。知识库只写两类东西——**去哪找**（导航）和**为什么这样**（决策记录）。「是什么」让 AI 临时去读代码；把代码描述抄进文档，就是给未来埋雷；
2. **宁可短而准，不要全而旧**。行业里有句糙话：宁可让 AI 写代码，也别让 AI 读旧文档；
3. **更新靠机制，不靠自觉**。「定期大扫除」必然落空；正确做法是把更新挂到已有事件上（任务收尾、PR、发版），让它顺带发生。

回看 05 章 5.3 的「记忆的层次」——会话内 / 项目级 / 跨项目。本章就是**项目级**这一层的完整展开。

## 11.2 四层模型：谁回答什么问题

把「AI 需要的项目知识」按**维护方式**分四层（而不是按内容主题分——这是全章的关键视角）：

| 层 | 载体 | 写者 | 更新时机 | 回答的问题 |
| --- | --- | --- | --- | --- |
| ① 常驻入口 | `AGENTS.md`（单源）+ 各工具转发文件 | 人 + AI 协助 | 每次纠错后随手补 | 项目是什么、命令、目录地图、「铁律」 |
| ② 导航层 | `docs/MAP.md`、`docs/modules/*.md` | AI 起草、人审定 | 结构变更时（挂 PR） | 改 X 功能去哪个包、入口在哪 |
| ③ 自动索引 | repowiki / 代码索引 / repo map / 符号检索 | 工具全自动 | 结构大改后重建 | 这个类在哪定义、谁在引用它 |
| ④ 经验层 | ADR、踩坑记录、非显而易见注释 | 人 + AI | 追加式，只增不改 | 为什么这样设计、别踩哪个坑 |

新会话里的定位链路：① 常驻加载（先有项目全貌）→ 任务来临查 ②（功能词翻译成包）→ 需要细节靠 ③（精确到符号）→ 遇到怪处读 ④（理解历史原因）。

维护成本自上而下递减：① 最小最常动，③ 零人工。**一条内容该放哪层，取决于它多久变一次。**

## 11.3 ① 常驻入口：单源 + 转发

### AGENTS.md 做单源

`AGENTS.md` 已是跨工具开放标准，被 Codex、Cursor、Jules、Amp 等原生读取（2026 年中已有 60K+ 项目采用）。两个特性正好服务知识库：**一份文件所有工具共享**；**支持子目录嵌套、就近覆盖**——monorepo 里可以让每个包目录放自己的 `AGENTS.md`，根文件只管全局约定。

各工具「转发」到单源的配置（规则文件全表见 02 章 2.2）：

| 工具 | 对 AGENTS.md 的支持 | 兼容做法 |
| --- | --- | --- |
| Codex CLI | 原生；全局 / 仓库根 / 子目录三级，就近覆盖 | 直接用 |
| Cursor | 原生支持（较新版本）；`.cursor/rules` 仍可用于目录级细粒度约定 | 直接用 |
| Claude Code | 2026 年起兼容读取：无 `CLAUDE.md` 时回退（2.1.277+ 起） | 稳妥做法：`CLAUDE.md` 只写一行 `@AGENTS.md` 导入 |
| Gemini CLI | 默认读 `GEMINI.md`，文件名可配置 | `settings.json` 设 `"context": { "fileName": ["GEMINI.md", "AGENTS.md"] }`（见模板） |

原则：**内容只写在 AGENTS.md 一处**，各工具的文件只做转发 / 导入——否则又多一份会腐烂的副本。

### 写什么（骨架）

```markdown
# AGENTS.md

## 项目是什么
一句话：XX 服务——为谁提供什么（第一句就要能回答「这个项目干嘛的」）

## 技术栈与命令
- 语言 / 框架 / 包管理器；构建、测试、lint 命令各一行

## 目录地图
- packages/auth/       认证（登录、token、权限）
- packages/reporting/  报表（导出、定时任务）
- apps/web/            前端主应用

## 铁律
- 不要动 legacy/ 目录
- 用 pnpm 而非 npm
- 数据库结构变更必须同步 docs/schema.md

## 在哪里查更多
- 功能 → 包映射：docs/MAP.md
- 架构决策：docs/adr/
```

### 体量原则

只放「每次会话都需要」的信息。规则文件会**全量常驻**上下文，写几百行等于稀释注意力——社区实测把 `CLAUDE.md` 删掉 70% 后，AI 反而更准。写不下的内容不是硬塞，而是**下沉**到 ② 层（docs/）并留一个指针。

## 11.4 ② 导航层：docs/MAP.md 模块地图

这一步直接解决「修 bug → 定位到包」。bug 报告说的是**功能词**（「导出报表报错」），代码组织用的是**目录 / 包名**——MAP.md 就是这张翻译表，也是 AI「不扫全库」的底气。这张表同时就是项目的**功能点清单**，人和 AI 看一眼就知道项目有哪些功能域。

```markdown
# docs/MAP.md — 功能 → 代码位置
> 更新规则：新增功能域 / 移动目录 / 更换入口时，更新对应行。
> 粒度：包级 + 一个入口文件；所有路径都应可验证。

| 功能域 | 包 / 目录 | 入口 | 测试 | 备注（非显而易见的定位信息） |
| --- | --- | --- | --- | --- |
| 用户认证 | packages/auth/ | src/AuthService.ts | tests/auth/ | token 刷新逻辑在 middleware 里 |
| 报表导出 | packages/reporting/export/ | ExportTask.ts | tests/export/ | 格式解析继承自 BaseExporter，核心不在本包 |
| 支付回调 | apps/api/src/payment/ | webhook.ts | tests/payment/ | 幂等键处理是历史坑，改前先读 ADR-0007 |
```

四条设计原则，都是为了「抗腐烂」：

1. **按功能域组织，不按目录树罗列**——AI 从功能词出发，人类写 bug 报告也用功能词；
2. **粒度到包 + 单个入口**，不要全文件清单——粒度越细，烂得越快；
3. **每行带测试目录**——这是留给漂移检测（11.7）的验证钩子：路径是否还存在，一查便知；
4. **备注只写「非显而易见」**——继承关系、核心逻辑不在此处、历史坑，这些是 AI 扫代码看不出来的。

大项目：MAP.md 保持索引级（一行一个功能域），每个功能域下钻到 `docs/modules/<name>.md` 二级文档、按需加载——就是 10 章讲过的渐进披露，粒度设计一脉相承。

## 11.5 ③ 自动索引层：不手写，定期重建

这层全部由工具生成，解决「精确定位到符号」（类在哪、谁在引用、入口函数是谁）：

| 类型 | 代表 | 说明 |
| --- | --- | --- |
| 仓库 wiki / 知识卡 | Qoder repowiki（`.qoder/repowiki/`） | 自动生成 wiki 与知识卡，支持语义检索 |
| 代码语义索引 | Cursor codebase index、Qoder | 语义搜索代码库；随改动增量更新，大改后重建 |
| repo map | Aider | tree-sitter 解析 + 符号排序的「仓库地图」，用地图代替全文进上下文 |
| 符号级检索 | Serena MCP（LSP） | 直接定位定义 / 引用 / 调用关系，比 grep 省 token |
| 自维护 wiki | LangChain OpenWiki（2026 新出） | CLI 生成 `openwiki/` Markdown wiki，可挂 CI 随提交更新，agent 经 MCP 读取 |

两条使用纪律：

- 把它们当**快照**：结构大改、大规模重构后重新生成一次；
- **永远不把它们的产出复制进 ①②**——③ 已经有答案，抄一份进手写层只会双份腐烂。

## 11.6 维护机制（一）：事件驱动更新

主机制只有一句话：**把「更新知识库」作为 AI 任务的收尾步骤**。写代码的 AI 此刻上下文里什么都有，顺手写一条成本最低；等你想起来「该更新文档了」，信息早凉了。

写进 `AGENTS.md`：

```markdown
## 知识库同步（任务收尾规则）
完成功能开发或 bug 修复后，检查并更新：
- 新增 / 移动目录、更换入口 → 更新 docs/MAP.md 对应行
- 形成架构决策 → 新增 docs/adr/NNNN-*.md
- 发现非显而易见的坑 → 补一行到对应模块文档备注
若无需更新，明确回复「知识库无需更新」。
```

再在 PR 模板加一行 checklist：`[ ] 若结构 / 入口有变化，已更新 docs/MAP.md`。你只审 diff，不做写作。

## 11.7 维护机制（二）：漂移检测（drift-check）

「定期更新」的正确形态是**定期检测**——让 AI 对比文档与代码现状、输出差异报告，而不是直接重写文档。封装成技能（为什么用 Skill 而不是纯 Command：见 10 章判例集——「改完代码就该被想起」的流程型知识）：

```markdown
---
name: drift-check
description: 检查项目知识库与代码现状是否漂移。在用户要求「文档体检 / 知识库检查」、发版前、结构性变更合并后使用。
---

# 知识库漂移检测

逐项执行，**只输出报告，不修改任何文件**：

1. 读 docs/MAP.md，逐行验证引用路径是否存在（目录 / 入口文件 / 测试目录），列出失效条目
2. 列源码顶层目录，找出未被 MAP.md 覆盖的功能域
3. 验证 AGENTS.md 的「目录地图」与「命令」：路径存在、命令可运行
4. 抽查 3 个 MAP 条目：读入口文件近 3 个月 git log，判断描述是否仍准确
5. 输出三类清单：失效 / 未覆盖 / 疑似过时，每条附建议改法
```

运行节奏：结构性 PR 合并后、发版前，或 CI 定时（每月）。发现漂移 → 让 AI 基于报告出修复 PR → **人审 diff 后合并**。红线：检测可以全自动，修改必须过审。

需要手动入口时，按 10.6 的「Command 入口 + Skill 内核」模式加一层薄壳（不重复流程内容）：

```toml
# .gemini/commands/drift-check.toml → /drift-check
description = "知识库漂移检测（复用 drift-check 技能）"
prompt = "使用 drift-check 技能执行知识库漂移检测，输出报告。"
```

## 11.8 度量：定位题回归测试

知识库有没有用，只能测。准备 3~5 道**定位题**，例如：

- 「改导出格式要动哪个包？」
- 「登录后 token 刷新逻辑在哪？」
- 「要加一个新报表类型，改哪几处？」

测法：**开新会话、只给题目、不给任何文件**，看 AI 能否不扫全库答对（第二题若能直接指到 middleware，说明 11.4 的备注生效）。答错 → 缺什么补什么：缺全貌补 ①，缺「功能 → 包」映射补 ②。大重构后、换模型后各重测一次——这就是知识库的回归测试。

## 11.9 老项目起步：项目探测（bootstrap）

已有项目建知识库，不用人工从零写——让 AI 扫一遍出初稿，你只做审定。任务模板：

```text
任务：为这个仓库建立项目知识库初稿，只写文档、不改代码。
1. 读 README、构建配置、目录结构、主要入口，产出 AGENTS.md 初稿：
   项目一句话 / 技术栈与命令 / 目录地图（带注释）/ 铁律候选 / 更多信息索引
2. 按顶层模块划分功能域，产出 docs/MAP.md 初稿：
   功能域 → 包目录 → 入口文件 → 测试目录
约束：
- 每一项都必须能从代码里验证；不确定的标 TODO，不要编造
- 最后单独列出：哪些条目是你的推测、需要人工核实
```

两个建议：先覆盖「近 3 个月改动最多的 5 个功能域」，不要追求一次全覆盖（需求驱动地长）；② 层的每一条都亲手抽查一遍——初稿的错条目比缺条目更危险。

## 11.10 反模式清单

1. **写成项目百科**——复述代码、贴实现细节：这是最快腐烂的部分，还会让 AI 偷懒，不去读真实代码；
2. **规则文件超长**——几百行的常驻内容会被模型稀释忽略；写不下就下沉到 docs/ 留指针；
3. **只建不更**——没有事件驱动 + 漂移检测，知识库三个月后就变成负资产；
4. **每个工具各写一份**——AGENTS.md 单源，其余转发；多份副本 = 多份腐烂；
5. **让检测自动改文档**——无审查的自动改写会引入新错误；报告自动出，修改要过审；
6. **追求全覆盖**——先用定位题测出最短路径，再按需扩展；
7. **MAP 粒度写到文件级全清单**——维护不住；包级 + 单入口就够定位。

## 11.11 落地清单

1. **建单源**：写 `AGENTS.md`（11.3 骨架），各工具配置转发（Claude `@AGENTS.md` / Gemini `context.fileName`）；
2. **建地图**：`docs/MAP.md` 先覆盖最常改的 5 个功能域（用 11.9 的任务模板生成初稿）；
3. **装机制**：agent 收尾规则写进 AGENTS.md + PR 模板加 checklist + 漂移检测技能挂 CI 定时；
4. **定节奏**：发版前跑 drift-check；结构大改后重建 ③ 层索引；每季度做一次定位题测试并补缺。
