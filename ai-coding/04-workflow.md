# 04 工作流实践

> 本章解决：把 AI 嵌入日常开发的完整流程——从需求到合并的每个环节怎么用、怎么控质量。

## 4.1 日常编码流

### 需求 → 设计

- 用对话模式澄清需求：让 AI 复述你的需求并列出歧义点
- 复杂需求先要方案：让它给 2-3 个备选设计 + 取舍分析，你来拍板
- 方案确认后落文档：让 AI 写成设计备忘（这正是 spec-coding 章节的起点）

### 实现

- **小步走**：每次改动聚焦一个逻辑单元，改完立即验证
- **测试同步**：实现功能的同时写测试；或先写测试再让它实现
- **频繁提交**：每个可工作的增量一个 commit，方便回滚
- **Plan 模式**：中大型任务先列步骤，确认后再执行

### 调试

1. 让它读完整错误信息 + 相关代码，先给出根因假设
2. 一次验证一个假设，不要让它盲改碰运气
3. 修复后要求：解释原因 + 补一个防回归测试

反模式：把 AI 当高级搜索引擎，贴报错要一个补丁就完事——你既没学到东西，也没验证它是否治本。

### 审查与合并

- **自查**：让 AI 先 review 自己的 diff（"找出这个改动里的问题"）
- **人工审查重点**：需求是否真的满足、边界条件、安全、性能、可维护性
- **PR 描述**：让 AI 根据 diff 生成变更说明与测试清单

## 4.2 中大型任务与多 Agent

### 任务拆解

- 大任务 → 子任务清单（带依赖关系与各自的验收标准）
- 每个子任务满足：可独立验证、可独立提交
- 复杂重构：先产出"改造计划 + 每步的回滚点"

### 多 Agent 协作模式

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| 串行委派 | 一个子任务完成后再做下一个 | 有依赖顺序的任务 |
| 并行探索 | 多个 Agent 同时尝试不同方案 | 技术选型、疑难 bug |
| 主从架构 | 一个 Agent 规划，其他执行 | 大型功能拆解 |
| 生成-审查对抗 | 一个写、一个审 | 关键代码质量把关 |

- 工具支持：Claude Code 的 subagents、Codex 的任务分解、云端 Agent 的并行任务
- 铁律：并行 Agent 不要操作同一批文件，否则合并冲突会吃掉全部收益

## 4.3 AI 代码审查

- **内置能力**：多数工具支持对 diff / PR 自动审查（Copilot、Claude Code 的 review 命令等）
- **专用工具**：CodeRabbit、Greptile、Qodo 等对 PR 自动评论
- **有效用法**：
  - 把审查标准写进规则文件（安全隐患、性能禁忌、风格约定）
  - 让 reviewer 给修改建议，不只是挑刺
- **局限**：AI 审查对"需求理解偏差"不敏感——业务正确性仍要人工把关

## 4.4 安全、隐私与合规

- **密钥泄露**：不要把 token / 密钥贴进对话；用环境变量 + .gitignore 兜底
- **提示注入**：AI 处理的网页、issue、第三方代码可能包含恶意指令，别让 Agent 全权限裸奔
- **执行权限**：Agent 执行命令需人工确认，或放进沙箱 / 容器运行
- **代码许可**：留意 AI 生成代码的许可证风险与公司合规政策
- **数据隐私**：敏感代码是否进入第三方模型，看清工具的隐私条款与企业版选项
- **依赖风险**：AI 推荐的新库先检查维护状态与安全记录
