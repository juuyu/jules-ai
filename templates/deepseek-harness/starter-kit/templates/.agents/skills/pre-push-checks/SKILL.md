# Pre-Push Checks（推送前检查）

这是指导，不是机械清单。目标：为本次外发改动取得**一次**最小充分证据。CI 拥有穷尽覆盖；本地不重复已通过的检查。

## 何时不用

- 改动尚未形成完整逻辑（先继续开发）。
- 用户明确要求跑全量、或正在诊断 CI 失败——此时按要求全量。

## 步骤

1. **确认改动面**：`git status --short --branch` + `git diff --stat <base>...HEAD`，列出触及的面（逻辑/接口/CLI/文件产物/文档/构建配置）。base 必须是从远端核实的 ref，不许猜。
2. **按面选证据**：
   - 业务逻辑 → 拥有该行为的聚焦测试文件或用例；
   - CLI/文件/外部产物 → 从外部重跑命令、重读产物验证（只检查 AI 自己的输出不算）；
   - 文档/配置/目录结构 → 链接检查、渲染预览、对应校验；
   - 公共接口/构建配置 → 完整 build + 冒烟；
   - 新增校验或护栏 → 准备负对照（无效输入必须被拒绝）。
3. **说明每条检查为哪个回归负责**，交决策者确认后执行。
4. **失败即停**：修完重跑该条；疑似环境问题需记录命令、失败用例、平台差异。禁止加超时/重试/弱化断言来掩盖不稳定测试。

## 验证

```sh
# 聚焦测试（示例，按项目实际命令替换）
<test-cmd> <相关测试文件>
# 护栏负对照：故意给无效输入，确认它变红/被拒绝
```

## 报告

只报告：实际执行的命令、关键输出摘要、未验证项清单。不许宣称未跑的检查通过；不许写「应该没问题」；推送失败不要寄希望于 CI 结果不同。
