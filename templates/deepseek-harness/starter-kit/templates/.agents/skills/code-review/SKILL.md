# Code Review（代码评审）

这是指导，不是打勾清单。一条有实据的阻断意见，好过一列风格 nits。

## 何时不用

- diff 只是格式化、机械重命名或自动生成产物（扫一眼即可）。
- 还没有可运行/可阅读的完整改动。

## 步骤

1. **建立改动面**：先看 diff stat 与完整 diff，列出涉及的模块、接口、配置、文档。
2. **先读要求，再读代码**：打开改动面触及的 AGENTS.md、模块 README、架构文档、相关 Agent Note；凭记忆评判是违规漏网的主要原因。
3. **按序检查**（前四类是阻断项候选）：
   - 正确性：接口两端、边界输入、错误路径是否一致；
   - 生命周期：异步/资源的创建与释放、取消与重试、并发竞争；
   - 安全：外部输入校验、凭据处理、权限边界；
   - 必需行为：是否破坏既有约定，文档/注释是否与代码同改；
   - 范围：diff 是否夹带无关改动、投机性抽象、没有消费者的公共方法；
   - 测试：断言是否验证外部可观察状态、是否在目标回归上会失败；新增护栏有没有负对照。
4. **核对证据**：作者声称跑过的检查是否实际存在于 PR 记录；语义缺口无法靠绿灯弥补。

## 报告

- 阻断项：每条给出 **缺陷 → 位置（文件:行）→ 影响 → 证据**；
- 建议项：简列，风格问题最多 3 条；
- 已被自动门禁保证的问题不报；
- 与 Agent Note 的分歧作为设计讨论提出，不是自动否决；
- 接收评审时逐条核实，凭技术理由修复或反驳，不做表演式认同。
