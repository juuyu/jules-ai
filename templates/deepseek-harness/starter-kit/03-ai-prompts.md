# 03 · 用 AI 生成这些文档：提示词集

> 复制提示词 → 替换尖括号占位符 → 发给 AI。所有提示词内置了 DSH 的四条写作纪律：
> **先读真源再动笔；一个事实一个家；备选方案只许记录不许编造；输出当前状态、不写改动史。**

## 使用原则

1. **先给上下文再给任务**：提示词一律先让 AI 读文件，禁止凭想象写（DSH 所有技能的第 0 步）。
2. **人负责事实，AI 负责成文**：决策理由、真实考虑过的备选方案只有你知道，提示词里要求 AI「信息不足就提问，不许编造」。
3. **产出即文件**：让 AI 直接按模板文件格式输出，你只做拷贝。
4. **写完用 P8 体检**：任何文档产出后过一遍 slop 清单。

---

## P0 · 项目初始化一把梭

```text
你是我的项目 AI 协作规范搭建助手。先浏览当前仓库的目录结构、package.json/构建配置、
现有 README 与 src 入口，然后产出以下文件（逐个完整输出，不要省略）：

1. AGENTS.md：按这个骨架——一句话定位 → 仓库结构（每个顶层目录一行注释，基于你实际看到的）
   → 常用命令（从 package.json/Makefile 实际提取，不许编造）→ 8 条以内约定
   →「编辑本文件」说明。总词数控制在 1500 以内，每条规则 1~3 行、自包含。
2. .agents/notes/README.md：决策日志规则一页纸（生命周期、何时写、alternatives 必填）。
3. .github/pull_request_template.md：Motivation / Changes / Testing(含 Proof 折叠区) 三段。
4. .agents/skills/pre-push-checks/SKILL.md 和 code-review/SKILL.md 两个技能。

要求：
- 命令必须来自真实配置文件；查不到的命令写「<待补充：实际命令>」，不要发明。
- 约定要匹配这个项目的技术栈，禁止贴与本项目无关的通用教条。
- 信息不足以判断时先问我，不要假设。
```

## P1 · 生成 / 更新根 AGENTS.md

```text
读取本仓库的 README、构建配置（package.json/pyproject.toml/go.mod 等）、目录结构后，
编写根 AGENTS.md。规则：
- 读者是每次新会话的 AI 代理；只放「每个会话都需要」的常驻规矩：结构、命令、约定。
- 每条约定 1~3 行，写断言而非倡议；能链接到详细文档的只留一行链接。
- 命令节每条命令加一行注释说明用途与边界（如「需要密钥」「CI 门禁」），
  并写明：提交前只跑覆盖本次改动的最小检查、不重复已通过的检查、只报告实际跑过的命令。
- 禁止内容：故事、示例走查、任何在别处有归属的细节、隐喻性大词（用具体名词）。
- 总词数 ≤ 1500。先输出你看到的命令清单让我确认，再出全文。
```

## P2 · 生成子树 AGENTS.md

```text
为 `<子树路径>/` 编写子树 AGENTS.md。先读：仓库根 AGENTS.md、该目录的 README 与主要源文件。
规则：
- 只写这个子树特有、根文件没有的规则；与根重复的内容一律删除。
- ≤ 500 词；每条规则一行断言 + 必要时一条相对链接。
- 如果这个子树没有任何特有规则（规则都在根文件里），直接回答「不需要子树文件」，不要硬写。
```

## P3 · 写 proposed note（决策前）

```text
我要做一个决策，请按 proposed Agent Note 格式帮我成文。先就以下素材向我提问补全，
禁止自行编造我没有提供的理由或备选方案。

决策主题：<一句话>
背景/痛点：<你知道的事实、相关文件链接>
初步方案：<你的想法>
真实考虑过的备选：<A… B…，哪怕只是想了一下；没有就说没有，我来补>

输出文件 `.agents/notes/proposed/<category>/<yyyy-mm-dd>-<topic>.md`，
category 从 feature/bug-fix/simplification/architecture/process/testing 六选一。骨架：
# Agent Note: <标题>
Status: proposed
## Problem          —— 写成不看方案也能独立成立的动机
## Proposal         —— 打算改什么，可以用将来时
## Alternatives considered —— 每个真实备选一个加粗引导段落 + 落选原因；没有真实备选时
                     明确标注「待我补充」，不许虚构
## Acceptance criteria —— 全部写成可观察、可验证的状态（命令输出/文件变化/行为），
                     不许写「更优雅」「更合理」
## Risks            —— 可能出错的事 + 本方案明确放弃什么
```

## P4 · proposed → implemented 转态（实施后）

```text
读取 `<proposed note 路径>` 与本次实际落地的代码改动（git diff：<base>..HEAD），
把该 note 转成 implemented 版本：
1. 路径移到 .agents/notes/implemented/<category>/，文件名日期保持首次提出日期不变。
2. Status: proposed → Status: implemented。
3. ## Proposal 改写为 ## Decision：现在时描述实际交付的现实——只写真正交付的内容，
   计划中被放弃/推迟的部分不得写成已完成。
4. ## Acceptance criteria 与 ## Risks 折入 ## Consequences：代价与收益都写，
   验收项改成「现在用什么测试/检查锁定该行为」。
5. ## Alternatives considered 原样保留。
6. 若实际交付与原提案不一致，列出差异清单先问我，不要替我圆场。
另请检查：本次 diff 是否改动了旧 note 中提到的路径/符号/默认值？列出需要同步事实的 note。
```

## P5 · 把重复流程固化成新技能

```text
帮我创建一个技能。先回答三个问题，信息不足就问我：
1. 这个流程我最近在哪些任务里重复交代过？（少于两次就不建议技能化）
2. 流程步骤与每步要读的权威文件是什么？
3. 结尾用什么具体命令/检查收口？

确认后输出 `.agents/skills/<kebab-case 名>/SKILL.md`：
---
name: <与目录同名>
description: <一句话，写「什么时候该触发 + 做什么」，这是 AI 判断是否加载的唯一依据>
---
# <标题>
开头一句定位（这是指导不是检查清单）。
## 何时不用      —— 边界与排除项
## 步骤          —— 第 0 步是「先读这些真源」；编号步骤
## 验证          —— 具体命令
## 报告          —— 固定输出格式 + 明确「什么不许宣称」
全文 ≤ 80 行；细节多就拆到 references/ 文件并在正文链接，不要堆长文。
```

## P6 · 代码评审

```text
对 <base>..HEAD 做评审。严格按这个顺序：
1. 先用 git diff --stat 与完整 diff 建立改动面清单（哪些模块、接口、配置、文档）。
2. 打开改动面触及的权威文件（AGENTS.md、相关 README、架构文档、对应 note），读完再看代码。
3. 逐条检查：接口两端是否一致；错误路径是否有处理所有权；异步/资源是否有完整释放；
   公共面是否有真实消费者；diff 是否夹带无关改动；文档/注释是否与代码同改；
   测试是否断言外部可观察状态而非复述实现。
输出：
- 阻断项（正确性/生命周期/安全/必需行为）：每条给 缺陷→位置→影响→证据，引用具体文件行。
- 建议项：简列。
- 已被自动门禁保证的问题不报；风格 nits 合并成最多 3 条。
没有实据的问题不提；一条有证据的阻断胜过一列猜测。
```

## P7 · 推送前检查

```text
我准备推送。请：
1. git status 与 git diff --stat <base>..HEAD，列出本次改动触及的所有「面」。
2. 为每个面选出最小必要检查（单测聚焦文件/外部命令复验/构建冒烟/文档校验），
   说明每条检查能为哪个具体回归负责——不要默认全量。
3. 等我确认后逐条执行，报告实际命令与输出摘要；失败就停，不要建议绕过。
4. 对本次新增的校验/护栏，给出一个负对照操作（无效输入应被拒绝），没有负对照要明确指出。
5. 列出本次未验证的项，禁止使用「应该没问题」类措辞。
```

## P8 · 文档体检（slop + CoT 泄漏）

```text
审查 `<文档路径>`，只报告问题与修改建议，不要直接重写。
A. slop 8 条逐条过：重复规则（同一规则多处出现）/历史错位（非历史文档讲「以前曾经」）/
   状态标注（「已实现！」「未来将」）/手工复述可生成的目录/推理实录（实现过程叙述、
   显然分支的证明）/同一理由在多处重复/段落墙/强调膨胀（到处加粗大写）。
B. CoT 泄漏测试：假设读者只有当前 HEAD 代码，没有任何会话记录、PR 线程和未提交草稿——
   文中每个引用他能解开吗？每个断言他能核验吗？列出解不开的句子。
C. 事实核查：文中每个命令、默认值、文件名去仓库实际比对；无法验证的标红，不要用记忆兜底。
输出三列：位置 | 问题类别 | 改法（搬家/删除/压缩/改成现状句）。
```

## P9 · 找简化点（周期性维护）

```text
扫描 `<目录或模块>`，找可以删除的维护义务（API、配置项、状态分支、依赖、文档、测试）。
对每个候选回答：
1. 它有完整的效果路径吗（生产者→转换→消费→可观察结果）？用 rg 给出真实引用，不许只看 import。
2. 删掉/合并它，哪个消费者的动作会改变？没有消费者改变 → 强候选。
3. 删掉后哪些维护义务消失？放弃了什么能力？重新引入的条件是什么？
4. 这是真简化还是把复杂度搬到别处？搬家式的标「非简化」。
输出候选清单（按收益排序）与证据链接，删除动作等我人工拍板，不要自行改代码。
```

## 提示词使用速查

| 场景 | 用哪个 |
| --- | --- |
| 新项目搭 AI 协作骨架 | P0 |
| 根/子目录规矩过期或缺失 | P1、P2 |
| 要做有取舍的决策 | P3（决策前）→ P4（实施后） |
| 同一件事口头交代超过两次 | P5 |
| 提交前、评审时 | P7、P6 |
| 文档越写越胖、AI 味重 | P8 |
| 定期清理技术债 | P9 |
