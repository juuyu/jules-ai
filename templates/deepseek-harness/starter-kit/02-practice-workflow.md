# 02 · AI 编程实践流程：一步一步怎么做

> 把 DSH 的纪律压成一条可执行的日常路线。每步给「动作 → 最小做法 → DSH 依据」。
> 适用对象：用 Claude Code / Gemini CLI / Trae 等 AI 编程工具的个人或小团队。

## 全景图

```text
一次性搭建                每个任务的循环                    周期性维护
─────────────            ──────────────────              ─────────────
根 AGENTS.md      ① 领任务·读规矩                            找简化点
notes 目录        ② 决策门（要不要写 note？）               归档/删除旧 note
2~3 个技能        ③ 写方案（proposed note）                 文档 slop 体检
PR 模板           ④ 实施（最小改动面）
                  ⑤ 自检（按改动面取最小证据）
                  ⑥ 提交·推送（note 转态 + PR 三段式）
                  ⑦ 评审回应（逐条核实，不表演式认同）
```

---

## 阶段 0 · 一次性搭建（半天内完成）

1. 在项目根放 `AGENTS.md`：仓库结构 + 常用命令 + 5~10 条约定（模板见 [templates/AGENTS.md](./templates/AGENTS.md)）。
2. 放入 notes 一页纸规则（[templates/.agents/notes/README.md](./templates/.agents/notes/README.md)）；首次写决策时在 `.agents/notes/implemented/` 下落第一条 note。
3. 放两个技能：`pre-push-checks`、`code-review`（[templates/.agents/skills/](./templates/.agents/skills/)）。
4. 放 PR 模板到 `.github/pull_request_template.md`。
5. 用 Claude Code：`ln -s AGENTS.md CLAUDE.md`；用 Gemini：把 `context.fileName` 指向 AGENTS.md 或加 GEMINI.md 转发。

**最小做法**：只做 1、2、4 就能开始。DSH 依据：根文件管常驻规矩、notes 存决策、PR 模板是人机共同接口。

---

## ① 领任务 · 读规矩

**动作**：动手前让 AI 先读三样东西——根 AGENTS.md、改动目录的子树 AGENTS.md（没有就跳过）、相关模块的 README/架构文档。

**最小做法**：任务开始时对 AI 说一句固定开场白：

> 「先读 AGENTS.md 和 `<目标目录>/` 的说明，列出本任务涉及的文件与约定，再给方案。」

**DSH 依据**：所有技能的第 0 步都是「先读真源」；code-review 技能原话——*凭记忆中的规则去评判 diff，正是违规能通过评审的方式*。

## ② 决策门：这个任务要不要写 note？

问一个问题：**代码、测试和现有注释，能解释这个改动的「为什么」和「放弃了什么」吗？**

| 情况 | 动作 |
| --- | --- |
| 机械改动、重命名、局部 UI 调整、照既定方案执行 | 不写，直接做 |
| 引入新约定、新架构关系、删除能力、修一个有争议的 bug、选了 A 方案否掉 B | **先写 proposed note，再动手** |
| 决策已经做完了才意识到 | 直接写 implemented note，与代码**同一个提交** |

**最小做法**：拿不准就写。一条 note 15~40 行，模板 [note-proposed.md](./templates/.agents/notes/note-proposed.md)。判断信号：你已经在对话里向 AI 解释「为什么这么做」超过两轮——这个理由就该落盘。

**DSH 依据**：*代码和文档无法承载的为什么以及放弃了什么*才进 notes；机械改动豁免；禁止重复记录，已有 owner note 就更新它。

## ③ 写方案：proposed note

**动作**：按骨架填五节——`Problem`（不依赖方案也能读懂的动机）→ `Proposal`（打算怎么改）→ `Alternatives considered`（**真实考虑过**的备选 + 落选原因，禁止事后编造）→ `Acceptance criteria`（什么可观察状态算完成）→ `Risks`（可能出错与明确放弃的东西）。

**最小做法**：用 [03-ai-prompts.md](./03-ai-prompts.md) 的 **P3 提示词**让 AI 起第一稿，你负责补 Alternatives（AI 不知道你真实考虑过什么，这一节必须人提供素材）。

验收标准写成**可观察**的：「运行 X 命令输出 Y」「文件 Z 不再包含 W」，不写「代码更优雅」。

## ④ 实施：最小改动面

给 AI 的四条硬约束（已写进模板 AGENTS.md 的约定节）：

1. **一次改动只携带声明的行为变化所需的行**——不顺手重构、不搬家无关代码（DSH：迁移是搬代码不是重写）。
2. **新行为走既有扩展点**，不新造分支体系；加新依赖前先确认它真的删掉了自有代码和测试。
3. **配置错误大声失败**，不写静默兜底；空 catch 要写清错误名和原因。
4. **注释只讲本地契约**（前置条件、失败模式、所有权），不复述代码、不写改动历史。

**最小做法**：任务大就先让 AI 给改动文件清单和顺序，确认后再逐文件执行；每完成一个文件对照清单勾掉。

## ⑤ 自检：按改动面取最小证据

**动作**：推送前先界定「本次到底改了什么面」，再选证据——**不是每次全量，也不是凭感觉**。

| 改动面 | 最小证据 |
| --- | --- |
| 业务逻辑 | 拥有该行为的单个测试文件/聚焦用例 |
| CLI / 文件 / 外部产物 | **从外部重跑命令或重读文件**验证（只 grep AI 自己的输出不算数） |
| 文档 / note / 配置结构 | 链接检查 + 渲染预览 + 对应校验脚本 |
| 公共接口 / 构建配置 | 完整 build + 冒烟 |
| 新增校验/护栏 | **负对照**：故意引入无效输入，证明它真的会拦 |

三条报告纪律（让 AI 结束时照做）：

- 只报告**实际跑过**的命令与关键输出；没跑的不许说「应该没问题」。
| 检查失败就停下修，**不赌 CI 结果不同**；环境问题要给出命令、失败用例、平台差异三件套。
- 不重复跑刚通过的检查；CI 负责穷尽覆盖与平台矩阵。

**最小做法**：没有自动化测试的项目，最低标准是「附命令 + 输出」，并让 AI 对未触碰文件做逐字节/逐行确认。

**DSH 依据**：pre-push-checks 技能全文；*e2e 断言要在外部重跑命令，只探测代理自己的输出会让作弊的代理通过*；*护栏只有在回归能让它变红时才算护栏*。

## ⑥ 提交 · 推送

1. **note 转态**：proposed 落地后，在同一提交里移到 `implemented/`，把 `## Proposal` 改写成现在时的 `## Decision`，验收标准与风险折入 `## Consequences`（P4 提示词可代劳改写）。
2. **implemented note 随代码同步事实**：本次改动若动了旧 note 里提到的路径/名称/默认值，顺手在同一提交更新——但只改事实，不反转决策。
3. **写 PR**：套三段式模板——Motivation 关联 issue；Changes 写两类可观察变化（没有写 **None**）；Testing 每方法一条 + Proof 折叠证据。
4. **推送后核对**：本地 HEAD 与远端一致；看 CI，pending 就报 pending，失败先查再归因。

**最小做法**：个人项目没有 PR 流程，就把三段式写进 commit message body，证据贴在消息里。

## ⑦ 评审回应

- 评审别人/AI 的产出时：先打开该 diff 触碰的权威文件，**再读 diff**（模板技能 [code-review/SKILL.md](./templates/.agents/skills/code-review/SKILL.md) 已固化）。
- 优先级：正确性 / 生命周期 / 安全 / 被破坏的必需行为 ≫ 风格。**一条有实据的阻断意见，好过一列 nits。**
- 报告格式：缺陷 + 位置 + 影响 + 证据；阻断与建议分开；已被绿门禁保证的问题不报。
- **接收评审**：逐条核实，凭技术理由修复或反驳，不做表演式认同；与 note 的分歧是设计讨论，不是自动否决。

## 周期性维护（每迭代或每月一次）

| 动作 | 怎么做（可用 P8 提示词） |
| --- | --- |
| 找简化点 | 让 AI 回答三问：这个能力有完整效果路径吗？这些区分改变哪个消费者的动作？删掉它哪些维护义务消失？把答案列成候选清单，人工挑——复杂度搬家不算简化 |
| 清理 notes | implemented note 只描述小机械改动的直接删；仍有指导价值的保留；有历史价值但不再指导的归档。新写 note 时顺带做取代检查 |
| 文档体检 | 用 slop 8 条扫一遍常驻文档；再用「the one test」查 CoT 泄漏：只有 HEAD 代码的读者能否解开每个引用？超词数预算就「搬家 → 压缩」 |
| AGENTS.md 减肥 | 根文件超过约 200 行/2000 词时，把细节降级进技能或子树文件，根里只留一行链接 |

## 决策速查卡（建议打印/置顶）

```text
开工前：读 AGENTS.md 了吗？
决策门：为什么/放弃了什么，代码自己说得清吗？说不清 → note
写 note：Alternatives 是真实记录的吗？
实施中：这行 diff 是本任务声明的行为变化需要的吗？
自检前：我验证的是「世界」还是 AI 的自我报告？
护栏：无效输入会让它变红吗？
报告时：我只写了实际跑过的命令吗？
提交时：note 状态与代码同 PR 了吗？PR 的空项写 None 了吗？
```
